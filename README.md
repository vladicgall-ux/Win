# WinFileRecovery

Десктопное приложение для Windows (WPF, .NET 8) для восстановления удалённых
файлов: прямое чтение секторов диска, разбор структур NTFS ($MFT) и FAT32
(записи каталога), а также сигнатурный carving по содержимому диска.

## Статус исправлений по аудиту безопасности (16.09.2026)

**P0 (критические) — сделано:**
1. Запрет восстановления на исходный физический диск — сравнение по
   `IOCTL_STORAGE_GET_DEVICE_NUMBER`, а не по букве тома
   (`Core/Disks/DiskIdentity.cs`), подключено в `MainViewModel.RecoverSelectedAsync`.
2. `RawDisk.ReadSectors` — полная проверка границ (отрицательные значения,
   overflow через вычитание, а не сложение, размер буфера).
3. Строгая валидация NTFS boot sector (`NtfsBootSector.Parse`) — диапазоны
   для всех полей, сверка заявленного размера тома с реальным размером диска.
4. То же для FAT32 (`Fat32BootSector.Parse`).
5. `DataRunParser` — отклонение отдельных повреждённых data run вместо
   доверия им; лимит правдоподобного числа кластеров.
6. Лимиты на глубокий carving-поиск (`SignatureCarver`: `MAX_RESULTS` = 100 000,
   `MAX_TOTAL_RECOVERED_SIZE` = 2 ТБ по умолчанию, настраиваются через
   конструктор) — поиск останавливается и явно предупреждает пользователя,
   если упёрся в лимит.

**P1 (важные) — сделано частично:**
- Проверка размера/экстентов каждого файла перед восстановлением
  (`RecoveryOrchestrator.ValidateFile`), лимит 200 ГБ на файл.
- Безопасные имена файлов: запрет `.`/`..`, управляющих символов, лимит
  длины, схема `photo (1).jpg` при коллизиях (`MakeSafeFileName`/`MakeUniqueSafeFileName`).
- Защита от path traversal — итоговый путь проверяется через `GetFullPath`
  на принадлежность папке назначения (`ResolveWithinDestination`).
- Одна повреждённая запись/файл больше не прерывает восстановление
  остальных — ошибка попадает в `RecoveredFileResult.Error` и в CSV-отчёт,
  а обработка продолжается.
- Authenticode уже был чётко промаркирован (`Valid`/`Invalid`/`NotSigned`/`Unknown`)
  без заявлений о безопасности файла — соответствует пункту 10.
- Минимальные права уже соблюдались: диск открывается только на чтение
  (`GENERIC_READ`), процессов/cmd/PowerShell приложение не запускает.

**P1 — сделано (продолжение):**
- **Format-aware carving** для JPEG/PNG/ZIP (и docx/xlsx/pptx как ZIP-контейнеров) —
  вместо поиска первого совпадения футера теперь идёт честный разбор
  внутренней структуры формата, что устраняет систематическое усечение файлов:
  - JPEG (`FormatValidators/JpegFormatValidator.cs`) — проходит по маркерам
    JFIF/EXIF сегментам, корректно пропускает entropy-coded scan data
    (включая byte-stuffing `FF 00` и restart-маркеры `FFD0-D7`), находит
    настоящий EOI. Раньше первый попавшийся `FF D9` внутри сжатых данных
    (а не в конце файла) давал обрезанное изображение.
  - PNG (`PngFormatValidator.cs`) — проходит по chunk-фреймингу
    (length+type+data+CRC) до `IEND` вместо поиска байтовой сигнатуры футера.
  - ZIP (`ZipFormatValidator.cs`) — проходит local file headers → central
    directory → EOCD по объявленным размерам записей. Работает для
    обычных (не streamed) архивов, которыми являются почти все
    docx/xlsx/pptx и большинство zip; потоковые архивы (general purpose
    bit 3) откатываются на старую эвристику.
  - PDF/MP4/GIF/RAR/EXE/WAV/MP3 — по-прежнему эвристика header/footer/MaxSize
    (менее приоритетные форматы для честного парсинга, задел на будущее).
- **Подпись `WinFileRecovery.exe`/установщика** — подготовлена инфраструктура:
  метаданные сборки (`Company`/`Product`/`Description`/`Copyright` в
  `WinFileRecovery.App.csproj`), опциональные шаги `signtool` в
  `.github/workflows/build-installer.yml` (активируются автоматически,
  когда в секретах репозитория появятся `WINFILERECOVERY_PFX_BASE64` /
  `WINFILERECOVERY_PFX_PASSWORD` — до этого шаги — no-op), SHA-256 установщика
  публикуется рядом с артефактом. **Публисher `YourCompany` в
  `installer/setup.iss` и `.csproj` — плейсхолдер, заменить на реальное
  юрлицо перед релизом** (сертификат покупать не буду за вас — отметил
  TODO прямо в файлах).
- **Проверка свободного места** перед восстановлением
  (`MainViewModel.TryCheckFreeSpace`) — сумма размеров выбранных файлов
  + 5% запас сравнивается с `DriveInfo.AvailableFreeSpace`; при нехватке
  восстановление не запускается и сообщается, сколько места нужно/доступно.
- **Логирование операций** (`Core/Logging/OperationLogger.cs`) —
  время/тип операции/результат/длительность/число найденных-восстановленных/
  ошибок пишутся в `%LOCALAPPDATA%\WinFileRecovery\logs\operations.log`.
  Намеренно **не** логируются: содержимое файлов, имена/пути восстановленных
  файлов, пароли, сырые данные диска.
- **Тесты** (`tests/WinFileRecovery.Core.Tests`, xUnit, гоняются в CI —
  `.github/workflows/tests.yml`): валидация boot-секторов NTFS/FAT32
  (корректный принимается, для каждого поля отдельно проверяется отказ на
  повреждённом значении), `DataRunParser` (валидные/повреждённые/переполняющие
  runs), безопасность имён файлов и защита от path traversal. Плюс
  **fuzz-smoke тесты**: 2000 случайных буферов на каждый парсер
  (`NtfsBootSector`, `Fat32BootSector`, `DataRunParser`, `MftRecord`) с
  фиксированным seed — ловят регрессию к необработанному исключению
  (`IndexOutOfRangeException` и т.п.), а не просто «работает на моих данных».

**Не сделано (следующий шаг):**
- Настоящий coverage-guided fuzzing (например, через SharpFuzz) — текущие
  fuzz-smoke тесты используют случайные, не эволюционирующие входные данные,
  это не замена полноценному фаззеру — пункт 16 (частично).
- `ArrayPool<byte>`/дальнейший memory-safety проход по хвостовым
  аллокациям — пункт 14.
- Telemetry-политика и update-security — не применимо, пока в приложении
  нет ни телеметрии, ни автообновления; появятся — учесть пункты 18–19.
- Итоговый release-чеклист (пункт 20) — большая часть автоматизируемых
  пунктов покрыта тестами/CI выше; финальные ручные пункты (VirusTotal,
  чистая VM, Defender) остаются за человеком перед конкретным релизом.

## Готовый установщик — без сборки на своей машине

В репозитории настроен GitHub Actions workflow
(`.github/workflows/build-installer.yml`), который сам собирает exe и
установщик на `windows-latest` — своя Windows-машина/Visual Studio не
нужна:

1. Откройте репозиторий на GitHub → вкладка **Actions**.
2. Выберите workflow **Build installer** → **Run workflow** (кнопка справа)
   → запустится на текущей ветке.
3. Дождитесь зелёной галочки (обычно 2–4 минуты).
4. Откройте завершённый run → в разделе **Artifacts** скачайте
   `WinFileRecovery-Setup` — это и есть готовый `.exe`-установщик.

Также при пуше тега вида `v1.0.0` workflow автоматически создаёт GitHub
Release с установщиком, приложенным к релизу.

## Требования

- Windows 10/11 x64
- Visual Studio 2022 (17.8+) или .NET SDK 8.0+
- Права администратора для запуска (raw-доступ к диску их требует)

## Сборка и запуск (для разработки)

```powershell
dotnet build .\WinFileRecovery.sln -c Debug
dotnet run --project .\src\WinFileRecovery.App
```

Приложение попросит подтверждение UAC при запуске — это ожидаемо
(`app.manifest` задаёт `requireAdministrator`), т.к. открытие
`\\.\PhysicalDriveN` без прав администратора завершится
`ERROR_ACCESS_DENIED`.

## Publish — сборка в один exe-файл

```powershell
dotnet publish .\src\WinFileRecovery.App\WinFileRecovery.App.csproj `
    -c Release -r win-x64 --self-contained true `
    -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true
```

Результат: `src\WinFileRecovery.App\bin\Release\net8.0-windows\win-x64\publish\WinFileRecovery.exe`
— один файл, не требующий установленного .NET Runtime на целевой машине.
Манифест (`requireAdministrator`) встроен в exe, поэтому Windows сама
покажет запрос UAC при запуске, без ручного «Запуск от имени администратора».

## Установщик (Inno Setup)

1. Установите [Inno Setup](https://jrsoftware.org/isinfo.php) (бесплатный).
2. Выполните `dotnet publish` как выше (installer/setup.iss ссылается на
   путь публикации).
3. Скомпилируйте скрипт:
   ```powershell
   & "C:\Program Files (x86)\Inno Setup 6\ISCC.exe" .\installer\setup.iss
   ```
4. Готовый установщик появится в `installer\Output\WinFileRecovery-Setup-1.0.0.exe`.

Установщик:
- запрашивает права администратора при запуске (`PrivilegesRequired=admin`);
- копирует единственный self-contained exe в `Program Files\WinFileRecovery`;
- создаёт ярлыки в меню «Пуск» и (опционально) на рабочем столе;
- регистрирует стандартную запись удаления в «Программы и компоненты».

Сам `WinFileRecovery.exe` при каждом запуске (в том числе из установленного
расположения) продолжает запрашивать UAC — это задаётся его `app.manifest`,
а не установщиком, и сохраняется независимо от способа запуска.

### Альтернатива: MSIX / Visual Studio Installer Projects

Если предпочтителен MSIX (для распространения через Microsoft Store или
корпоративный деплой) — используйте `dotnet publish` с
`-p:WindowsPackageType=MSIX`, либо расширение **Visual Studio Installer
Projects** для классического .msi. Оба варианта тоже должны включать
`requireAdministrator` в манифесте приложения — сам манифест не меняется.

## Фильтр по периоду удаления

Над списком найденных файлов можно задать диапазон дат «С... По...» —
список сразу отфильтруется, и «Выбрать все» отметит только показанные
(отфильтрованные) файлы.

Важно: ни NTFS, ни FAT32 не хранят точную дату удаления файла. В качестве
приближения используется:
- **NTFS** — время последнего изменения самой MFT-записи (`$STANDARD_INFORMATION`,
  поле "MFT changed"). Оно обновляется в момент удаления файла (запись
  переписывается), поэтому обычно совпадает с датой удаления с точностью до
  минут — но так же обновится при простом переименовании или изменении
  атрибутов, если это случилось незадолго до удаления.
- **FAT32** — дата последней записи файла (`LastWriteTime`) из записи
  каталога — это дата последнего *изменения* файла, а не удаления
  (FAT вообще не хранит момент удаления отдельно).
- **Глубокий поиск (carving)** — даты нет вообще, метаданных файловой
  системы для найденных файлов не сохранилось. При активном фильтре такие
  файлы скрываются из списка (лучше спрятать, чем ошибочно показать/скрыть).

## Проверка целостности после восстановления

После записи каждого файла приложение автоматически:

- считает **SHA-256** восстановленных байт (`Core/Verification/Sha256Hasher.cs`);
- проверяет **Authenticode-подпись** через `WinVerifyTrust` из `wintrust.dll`
  (`Core/Verification/AuthenticodeVerifier.cs`) — статус: `Valid` (подпись
  верна и доверена), `Invalid` (файл подписан, но подпись повреждена/не
  доверена — признак битого восстановления), `NotSigned` (подписи нет —
  **нормально** для документов, фото, видео и т.п., это не ошибка),
  `Unknown` (проверить не удалось).

Результаты видны во вкладке **«Отчёт восстановления»** и дублируются в
`recovery_report.csv`, который создаётся в папке назначения при каждом
восстановлении.

Важно: Authenticode есть только у подписываемых форматов (.exe, .dll,
.msi, .cab, подписанные скрипты) — если вы восстанавливаете, например,
`.docx`/`.jpg`/`.mp4`, статус `NotSigned` ожидаем и ничего не говорит о
качестве восстановления. Судить об успехе восстановления таких файлов
нужно по SHA-256 (совпадает с оригиналом, если он у вас есть отдельно) и
по тому, что файл открывается штатным приложением без ошибок.

## Важные ограничения текущей реализации

- **FAT32**: короткие имена восстанавливаются точно; длинные имена (VFAT
  LFN) не реконструируются, так как их записи-продолжения помечаются
  удалёнными независимо от короткого имени и ненадёжны. Каталоги читаются
  в пределах первого кластера (без прохода по цепочке FAT для очень больших
  каталогов).
- **NTFS**: восстановление по фрагментированным `$DATA` (несколько data
  runs) поддержано корректно; цепочка кластеров самого `$MFT` берётся из
  его собственных data runs, с эвристическим fallback, если запись 0
  повреждена.
- Всегда восстанавливайте файлы **на другой физический диск**, отличный от
  сканируемого — запись на тот же диск может перезаписать ещё не
  восстановленные удалённые файлы.
- Recovery работает по best-effort: как только удалённые сектора/кластеры
  перезаписаны новыми данными, восстановление конкретного файла уже
  невозможно ни одним инструментом.
